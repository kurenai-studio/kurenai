# Wanaka Game Specialist

Resolve the Wanaka-owned boundary in front of you, then write ordinary TypeScript. Use the relevant guide for the game mechanic, asset, or Engine integration being implemented.

## Skill files

- `references/engine-api/*.d.ts` — generated declarations and API authority for the reviewed public Engine import subpaths. A nested subpath joins its segments with dots: `wanaka-studio-engine/default-characters/blond-beard` is `references/engine-api/default-characters.blond-beard.d.ts`. Read the declaration matching the import you need; if it disagrees with a guide, the declaration wins.
- `references/guides/*.md` — reviewed prose: Engine API integration, cross-cutting authoring guidance, and troubleshooting. Guides are not API authority.
- `examples/*.ts` — closed Engine API integration slices compiled against the shipped Engine. They prove a boundary. [default-third-person-character.ts](examples/default-third-person-character.ts) is the character-game project starter when the brief does not name an appearance. [third-person-character.ts](examples/third-person-character.ts) is the compositor for an already loaded model. [arcade-racer.ts](examples/arcade-racer.ts) shows arcade simulation ownership, independent display interpolation, and a camera sharing the display pose. [top-down-follow.ts](examples/top-down-follow.ts) is the default rigid top-down follow slice.

## Local asset inspection

Catalog GLBs referenced by the current project may be available as best-effort local copies at `/tmp/game_assets/<assetId>.glb`. Bash can inspect these files when raw model information is useful. Preparation runs in the background: if the exact `.glb` path is absent, a matching `<assetId>.glb.COPYING.*` file marks an incomplete or in-progress cache write and must not be read. Inspect only the exact `.glb` path after it appears. Node names ending `_LOD` plus a positive integer are authored detail branches: `model3DLoader.load` converts them into exclusive `THREE.LOD` levels. Confirm `isLOD` on the returned tree. Read [model-parts-and-attachments.md](references/guides/model-parts-and-attachments.md) before attaching into those models.

## Using a sidecar

For heavy games, show a lightweight loading view before starting expensive initialization; do not block its first activation on that work. Scope and catch background loading, and keep gameplay disabled until its required assets and collision are ready.

1. Read only the generated declaration matching the public Engine import subpath you need. If the unresolved call imports from the Engine package root, read `references/engine-api/wanaka-studio-engine.d.ts`.
2. Import that public Engine subpath directly. Do not copy declaration-only types into project source.
3. Choose the phase by what the work is: `fixedInput` and `fixedUpdate` for fixed simulation, `update` for ordinary frame gameplay, `preRender` for presentation sync.
4. Let the simulation sidecar own the poses it simulates and present them afterward. Ordinary Three objects around it stay project-owned.
5. If a real compile or export-resolution diagnostic points at a package mismatch, inspect only that narrow declaration or export surface.

## Reference routes

- Toolbox presets, scoped actions/equipment/UI/VFX edits, PCG Seed changes and Tune requests:
  read [Toolbox integration](references/guides/toolbox.md) before editing. The final player request
  overrides preset defaults; pinned targets and task details must be re-resolved against current source.

These routes cover the high-traffic contracts. They are reviewed guidance, not an API inventory; the generated declaration for the imported subpath is authoritative.

Character-driven 3D games start here:

- PhysicsWorld + named Player + CharacterController + keyboard move/jump + follow camera: [default-third-person-character.ts](examples/default-third-person-character.ts) when the brief does not name an appearance and the stylized default body fits the game's tone. It loads `WANAKA_DEFAULT_CHARACTER` through `model3DLoader`, names the model `Player`, and passes `{ clipNames: WANAKA_DEFAULT_CHARACTER.clipNames }` into [third-person-character.ts](examples/third-person-character.ts). That compositor submits one `control(intent)` per fixed step. `setMoveIntent()` is the low-level escape hatch: it does not carry facing, jump, stance, or a control sequence, and MUST NOT mix with `control()` in the same step. Name every playable `Object3D` (for example, `model.name = 'Player'`). When the brief names an appearance or calls for a realistic, military, or genre-specific aesthetic where stylized cartoon default bodies would clash, source a matching character via `search_native_assets` or `generate_game_asset` + `prepare_character`, load that installed ProjectFile through `model3DLoader`, then call [third-person-character.ts](examples/third-person-character.ts) with the returned Group. When using the stylized default character set, additional grounded NPCs MUST import one other published body such as [default-character-blond-beard.ts](examples/scenes/default-character-blond-beard.ts) (`wanaka-studio-engine/default-characters/blond-beard`, `wanaka-studio-engine/default-characters/purple-hair`, `wanaka-studio-engine/default-characters/gold-twin-tails`, `wanaka-studio-engine/default-characters/pink-bob`, or `wanaka-studio-engine/default-characters/black-headscarf`) and load it the same way. Do not import `wanaka-studio-engine/default-characters`; that module stages every published body. When a loaded biped humanoid character needs locomotion or authored actions, follow the animation-readiness procedure in [assets.md](references/guides/assets.md#character-models) before implementing that behavior.
- Grounded walking NPC movement and facing: [character-ai.ts](examples/character-ai.ts). Navigation waypoints use the same handoff in [character-navigation.ts](examples/character-navigation.ts); both submit `movement: { kind: 'world', velocity }`. Flying enemies, turrets, and simple kinematic hostiles keep project pose and heading; do not force a grounded CharacterController. Use [navmesh-walk.ts](examples/navmesh-walk.ts) only when `NavigationAgent` owns an ordinary `Object3D` exclusively.
- Animated presentation layering: [animated-model-layer.ts](examples/animated-model-layer.ts). Navigation locomotion goals and target-facing behavior: [locomotor-goals.ts](examples/locomotor-goals.ts).
- Physical NPC or bot walk: one `LocomotorWorld` on a `NavigationMesh`, then `Locomotor.create` per `CharacterController`. Goals and status branching: [locomotor-goals.ts](examples/locomotor-goals.ts). Do not attach `NavigationAgent` to that character or write `position`.
- Bound-character clips follow `latestStep`. Masked upper-body overlay: [animated-model-layer.ts](examples/animated-model-layer.ts). Head look and weapon aim: [look-at.ts](examples/look-at.ts). Follow camera: [camera-rig-third-person.ts](examples/camera-rig-third-person.ts). First-person eye: [camera-rig-first-person.ts](examples/camera-rig-first-person.ts).

- Leaderboard: [leaderboard.ts](examples/leaderboard.ts). Consume the injected `PlatformBridge` host only — never put API origins, player tokens, or Wanaka HTTP calls in project source. - BGM and sound effects: [audio-session.ts](examples/audio-session.ts) and [assets.md](references/guides/assets.md#audio-loudness-and-processing). Read `references/engine-api/audio.d.ts`. Use `createAudioPlayback` to create one `AudioSession` on the Play scope, preload the music and cue set, and reuse it for every clip. A second session shares the browser audio context and the host master volume, and adds another listener. Call `bindAudioControls` or the `*FromGesture` methods from user gestures; spatial playback passes the native Object3D. Measure installed audio files under `assets/` with `ffmpeg` / `ffprobe` in Bash and balance channel or per-clip volume instead of guessing gains. Do not construct a separate audio source.
- Before selecting parts from a compound GLB, attaching one loaded model to another model's node or animated bone, or when a GLB inspection lists `_LOD*` names, read [model-parts-and-attachments.md](references/guides/model-parts-and-attachments.md).
- Multiplayer room API: an online build starts with the `wanaka:wanaka_game_multiplayer` Skill. [multiplayer-rooms.md](references/guides/multiplayer-rooms.md) — includes `platform.roomSession` (create / invite link / ready / start) and factions as waiting-phase simulate state, checked by the game before Start. Keep room-session UI mounted and start `sim`-backed play only after Start — [roomsession-play.ts](examples/roomsession-play.ts). [room-controlled-character.ts](examples/room-controlled-character.ts) attaches unspecified appearance on Play: copy the collision object's pose directly onto a catalog GLB, because `{ object }` writes the capsule bottom and the published body root is feet-origin. Jump and fall clips require `{ model }`, which entity `create` cannot await.

Cross-cutting craft — native Three work that still has a Wanaka-owned ownership rule or diagnostic method:

- Scene catalog, switching, and non-coplanar surface layering: [scene-config.md](references/guides/scene-config.md). Keep overlapping ground, road, plaza, ramp, and wall decal faces offset by at least `0.02` units along their normal so they do not z-fight or trigger `Coplanar surface overlap detected` in Game Test.
- Queryable water (compute pond, Wave Ocean, swim/buoyancy sampling): [water-surface.ts](examples/water-surface.ts). Do not invent a transmission disc; gameplay samples height and normal through `sampleWaterSurface`.

## Genre routing

- Original whole-game floor: read [good-game scaffold](references/guides/_good_game_scaffold.md) before the genre guide; skip it on a bounded edit whose gameplay owner is already established.
- Route selection, cross-genre composition, and camera/control overrides: read [genre-routing.md](references/guides/genre-routing.md) to pick the primary guide or compose mechanics across multiple guides (while keeping one writer per state, input, camera, transform, and persistence channel), or when the brief asks for a camera, projection, or control style outside a guide's default.
- Racing or driving: read [3D Racing](references/guides/genre_3d_racing.md) before implementing the vehicle, course, or race rules. Default **arcade racer** requests use the project-owned integrator in [arcade-racer.ts](examples/arcade-racer.ts); use `VehicleController` only when the brief asks for simulation wheeled physics.
- RPG (any subgenre — open-world, 3D soulslike/action/monster-hunting ARPG, first/third-person shooter RPG, isometric hack-and-slash loot ARPG, turn-based JRPG, tactical grid SRPG, or dice-check CRPG): ALWAYS load **both** [RPG](references/guides/genre_rpg.md) (for the role-playing world/NPC/quest stage, progression/build systems, and unified `C/I/K/J/Esc` menus) **and** the matching combat/exploration guide — in particular, cross-genre shooter RPGs (such as *Cyberpunk*, *Fallout*, *Starfield*, *Mass Effect*, or *Borderlands*) MUST load **both** `genre_rpg.md` and [Shooter](references/guides/genre_fps_tps.md) (retaining full viewmodel/over-shoulder aim, ADS, recoil, `--wk-reticle-gap` reticle, and shot/hit feedback), and real-time action/hunting RPGs (such as *The Witcher*, *Elden Ring*, or *Monster Hunter*) MUST load **both** `genre_rpg.md` and [Action Combat](references/guides/genre_rpg_action_combat.md). Never load `genre_fps_tps.md` or `genre_rpg_action_combat.md` alone for an RPG, and never skip them when the RPG features shooting or real-time melee.
- Roguelike / Roguelite / Survivors: read [Roguelike](references/guides/genre_roguelike.md) for run-based seeds, room/node graphs, per-run build drafting, permadeath resets, and optional meta-progression, or [Top-Down Survivors](references/guides/genre_roguelike_topdown_survivors.md) for auto-attacking `bullet-heaven` / `survivors-like` swarms.
